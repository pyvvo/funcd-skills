# funcd

funcd is newer than most training data, and its kinds and fields change between releases. Read its docs before you
write: they describe the latest release, and every page has a Markdown copy. Never write a kind, a field, a flag or a
status reason that a page does not show.

## Workflow

Copy this checklist and tick it off:

```
- [ ] 1. Find the topic in the docs index below and read its page (the .md URL)
- [ ] 2. For each kind you write, read its Spec tab (the page's spec.md) for the exact fields
- [ ] 3. Start from the closest example of the page or of the example repositories
- [ ] 4. Run it locally with funcdctl dev
- [ ] 5. Check each manifest with apply --dry-run; fix and repeat until it passes
- [ ] 6. Apply, then read the status until Ready; look up any other reason in the page's Status table
- [ ] 7. Call it and read its logs
```

**1–2. Read.** Fetch the page's URL from the index. With no network, read the same page under
[references/](#offline-references), which holds the Usage pages but not the Spec tabs. The API reference matters only
for a client that calls the HTTP API itself: funcdctl covers its operations.

**3. Examples.** [funcd-typescript](https://github.com/pyvvo/funcd-typescript/tree/main/examples) and
[funcd-python](https://github.com/pyvvo/funcd-python/tree/main/examples) hold Functions;
[funcd-functions](https://github.com/pyvvo/funcd-functions) holds Apps. Copy the closest one rather than starting
from nothing.

**4. Run locally.** Install the dev build of funcdctl (the Install page) and put Node.js, or Python for a Python
Function, on the `PATH`. Then, in the folder that holds the resource files:

```sh
funcdctl dev --gport 8080 --cport 8081
```

It runs the folder's resources on an embedded platform, prints each Function's URL, and streams the logs. Point the
other commands at it, in another terminal:

```sh
export FUNCD_SERVER=http://127.0.0.1:8081 FUNCD_TOKEN=funcd-dev-token
```

Its limits are on each page's *Run it locally* section: namespace `default` only, state in memory unless `--persist`,
no caller authentication, no egress control.

**5. Validate.** This catches an unknown field, a wrong value or a missing reference before anything is stored:

```sh
funcdctl apply --dry-run -f <file>
```

A good file prints `would apply <Kind>/<name>`. Otherwise the message names the document, the field and the rule, such
as `json: unknown field "tablez"` or `manifest is invalid (Route "api")` with the field after it. Fix that field from
its Spec tab and run the check again. Only go on when every file passes.

**6. Status.** `funcdctl get <kind> <name> -n default -o json` prints the status. Repeat it until the condition
`Ready` is `True`. Any other reason is listed, with what to do, in the *Status* table of the kind's page; a CLI error
is in its *CLI errors* table.

**7. Call and read logs.** Call a Function at the URL that `funcdctl dev` printed, such as
`curl -X POST -H 'content-type: application/json' -d '{...}' http://127.0.0.1:8080/function/<name>`, and read
`funcdctl logs <name> -n default`. A 422 means the data does not match the Function's contract.

## funcdctl

funcdctl applies resources to a funcd server and reads their state and logs, as kubectl does for Kubernetes. It
reaches the server that `--server` or `FUNCD_SERVER` names, with the token of `--token` or `FUNCD_TOKEN`. Before you
use a command or a flag, read its section in [references/funcdctl-commands.md](references/funcdctl-commands.md), which
lists every command with its usage, its text and its flags, or run `funcdctl <command> --help`. The dev build adds
`funcdctl dev`.

## Rules

- Generate a handler's input and output types from its contract with `funcdctl types`; do not write them by hand.
- A field that the Spec tab marks as set by funcd (a `status`, a Revision) is never written in a manifest.
- On a funcd server, use the server's URL and a token the operator gave; `funcd-dev-token` works only on loopback.
- When a page and your memory disagree, the page wins. When the page says nothing, say so rather than guess.
